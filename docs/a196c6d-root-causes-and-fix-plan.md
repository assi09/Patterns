# Why the same failures recur in PR 195

> **Historical record** (added to the repository on 2026-11-21), kept as written. It describes PR #195 before it was merged; #195 was merged on 2026-11-22 as `2ce08b5`. For what is true now, see [current.md](current.md).

Reviewed November 21 at `a196c6d58631651ee195df94ec3cafa476520cb1`. This is an implementation proposal based on the [independent live audit](independent-audit-a196c6d-handoff.md), its saved reader attempts, tool errors, replies and state snapshots. The fixes below have not been implemented or evaluated. The two offline probes described below used the current functions and synthetic fixtures.

## Decision for Claude after reviewing the earlier audits

**Start with one vertical slice: a follow-up edits a prior result or card. Prove that slice with the real reader before expanding it to the rest of the application.** Implement two operations first: change the interval of a metric read, and change the day of a paused workout. They cover a read and a write, and each has an independently checkable expected outcome. Use the same principles of reference and explicit change, with separate types for a result and a draft. A single universal schema for every task would recreate the problem the clause redesign fixed.

### What I verified offline across both independent decks

I supplied the intended reference edge, displacement, new boundary and length from the frozen scenario definitions to the current `period_window` function. I compared the computed dates with each deck's frozen expected dates. It reproduced **48/48** windows (24 from b730 and 24 from a196). The delivered live answers had passed **30/48** on those decks. This is an oracle-input control: it proves that the executor represents these cases, and says nothing about how accurately a model will extract those inputs from fresh language.

I also compared each failed live answer's published window width with the requested width. A width check alone would catch **5/18** failures: 1/9 on b730 and 4/9 on a196. The other 13 had the correct number of days on the wrong side of the landmark or at the wrong date. This is why adding a width regex, or asking another model to check arithmetic, is a poor use of the remaining budget. The important decision is *what date the person anchored to and what role it plays in the new interval*.

### The implementation and the stop decision

1. **Make the previous result or card explicit input.** Give the reader a small account-scoped list of addressable objects with stable IDs, dates/roles and allowed edits. Preserve mixed-clause support and explicit new topics. A date edit on a draft receives its local date, active duration and elapsed duration. Today and the draft date are distinct possible anchors. A comparison is one object with two labelled periods.
2. **Use the LLM where it can change the outcome.** The project already uses the small model in `OpenAILLM.read_request`. For the two operations above, use it to select the referenced object and extract only the requested change from natural language. Where practical expose concrete alternative interpretations with their date ranges, including an abstain choice. Build choices from the exposed object and clause quantities; avoid generating all possible dates or using regex to decide the semantics. A user can change several fields in one clause. Support that explicitly, and leave every other field absent. Check source spans for changes and enforce operation compatibility in code. Spans help diagnose unsupported edits but do not guarantee the model understood them.
3. **Have one executor per operation.** Resolve and store the selected dates once, and use them in the query, evidence and reply. Apply a supported draft edit to the persisted card before invoking any generative draft path. Reject a replacement that changed an untouched field. Keep status and confirmation grounded in the store. These changes reuse the current calendar and draft functions.
4. **Choose the model empirically.** Freeze realistic paraphrases and close counterexamples before testing. Run the baseline and the proposed interpreter on identical prompts, with both the previous object and expected edit recorded privately for synthetic fixtures. Compare the first reading, resulting dates/card, unnecessary clarifications, latency and cost. If the small model still loses the anchor, test a stronger reader on the *same ambiguous slice*. An extra verifier gets considered only if it improves net full passes, including good readings spoiled by retries. Jev's routing score alone does not identify a temporal anchor or authorize a field update.
5. **Make one go/no-go decision before further redesign.** First use the historical cases as development data. Keep one genuinely unseen deck for the end, including a new phrasing author if available. Grade both phrasings together, and separate forward, preceding, trailing and shifted windows. Include new-topic controls, two previous periods, out-of-range dates, paused edits, and a real duration change. Compare both the store and the user-visible response through the normal API. If the simpler edit design does not improve exact scopes on the matched evaluation, stop expanding it and inspect the first wrong field. If a live release gate still fails, keep that behavior behind an explicit limited-release decision; do not silently reclassify the miss or tune the held-out deck. Price any live comparison before running it.

For the other families, land the deterministic corrections in sections 4–7 in parallel development if convenient, but evaluate them independently. Preserve the tested evidence-versioning and guidance paths. The remaining discretionary question is model capacity. A stronger model's gain cannot be established from an offline executor test. Conversational semantic parsing research provides a relevant precedent for deriving a new structured query by editing the previous one. It does not give an accuracy estimate for this app. [Zhang et al., EMNLP 2019](https://aclanthology.org/D19-1537/)

## 1. Give the reader a smaller task when a user edits a time window

**Failure location.** All nine wrong metric follow-ups resolved on their first reader attempt. Three selected a whole-range shift, two selected a rolling interval anchored to today, one selected inheritance and three selected the edge-based operation but produced the wrong dates. The stored outline omits the individual edge parameters, so assigning blame to a particular parameter in those last three would be speculation. The requested metric and mean survived. The math in `requests.period_window` then executed the accepted representation. Jev reclassification downstream cannot correct that plan. Adding the edge operation made the right answer expressible; it left the other semantically different operations selectable.

**Proposed implementation.** Split selecting a referent from editing its range. For each data clause expose the actual eligible result IDs and labelled windows. Have the existing reader identify what is explicit in the current clause: referent, reference to today if present, landmark (first or last day), displacement, requested width, and which boundary the user is defining. Attach the supporting clause span to each *changed* field. Represent omitted fields as absent. For a derived interval, normalize shift, keep, trailing and leading blocks into one computation: resolve one anchor day, add the displacement, place the specified boundary there, and construct the opposite boundary from the requested width. A whole-range shift inherits the old width only when no new width was supplied. Retain separate constructors for standalone calendar dates and genuinely calendar-anchored periods.

Use the prior window and the explicit constraints to restrict the executable plans. For an unambiguous “four days,” eliminate every five-day result. For a prior-period landmark without a reference to the current day, eliminate today-based plans. Enforce start/end relationships as well as length; a four-day window on the wrong side still has length four. Validate both ends against the cited tool invocation. A valid quote by itself does not establish the model interpreted it correctly. If two distinct date ranges still satisfy the extracted constraints, resolve the choice from context or ask one concrete question naming both ranges. Do not ask when different interpretations produce identical dates. Keep a legacy adapter for stored conversation state.

**Experiment before replacement.** Replay the saved time turns with the existing plan, then shadow the constrained reader on exactly the same inputs. Grade anchor, requested width, two actual endpoints, answer, extra calls and unnecessary questions separately. Randomize the clock, prior interval, leap boundary, numbers and paraphrases. Include genuine whole-range shifts, new-topic “last week,” two prior periods, and two clauses with different dates. Splitting recognition from calendar normalization has precedent in temporal parsing; whether this particular reader benefits needs a held-out comparison. [SUTime paper](https://aclanthology.org/L12-1122/)

## 2. Persist the investigation the user is discussing

**Failure location.** One “three distinct ideas” follow-up became `other` on the first read. Its answer used a 60-day window. Another investigation selected the right kind but emitted no period or usable reference. In `requests._investigation` the empty part can disappear; in `ask.py` the named window list exists only on the investigation path. For the reverse-order comparison the reader emitted two valid periods, earlier first. The overview displayed that earlier period against the later one, then the next answer described the backward direction without dates.

**Change.** Save an investigation result with a stable ID, the compared windows and roles, the requested metric set, the dataset/source, and supported follow-up operations. Preserve the distinction between “A relative to B” and “what changed between A and B”; for the latter use later minus earlier and label both. Carry the comparison as a single referent. Asking for explanation, an option, or more points edits the response goal. It should retain the comparison unless the user changes it. If a habit tool needs a single focal window, explicitly bind it to the focal period and disclose that scope. With two unlabelled candidate referents, ask only if choosing one changes the result. Allow an intentionally new broad question to use the normal default. Make a fresh default window an explicit decision, inspectable at the tool boundary. Test temporal gaps between turns and preserve historical state compatibility.

## 3. Treat draft corrections as edits to the current card

**Failure location.** Both paused workouts were correctly drafted. In one date-only correction the reader nevertheless returned `duration_minutes=50`. The tool can enforce this value as both active and elapsed duration. The stored replacement lost the 12-minute pause. In the other, the reader returned November 1, one day after the synthetic clock, instead of October 22, one day after the card. The schema's `_day` allows an absolute date or an offset from today; the reader receives a pending-card boolean and previous questions. It has no direct structured reference to the draft date in this operation. The action trace then records `wrong_day` and fallback `invalid_log`. The latter code alone does not identify the failing field.

**Offline control.** I called `api.chat.corrected_payload` with the actual prior synthetic payload, the intended new date and no duration edit. It preserved 2,280 active seconds and 3,000 elapsed seconds. Use that deterministic operation first for supported edits. Currently the API invokes it after an unsuccessful model proposal.

**Change.** Pass an account-scoped draft reference and the minimal editable fields to the reader. Return a typed change such as “move this draft forward one local calendar day,” anchored to that card. Require current-turn support for each field being changed. A reference to preserving active minutes does not authorize writing a new duration. Apply the patch to the stored card in one transaction, checking that its revision still matches. Reuse existing zone and UTC elapsed-time arithmetic. Verify unchanged fields, including active time, elapsed time and pause, before superseding the card. Route genuine conflicts (for example a new end before the start) to a field-specific clarification. A card-level success must describe the stored replacement. Verify concurrent edits, repeated requests, daylight-saving transitions, a real duration change on an unpaused workout, and ambiguous active-versus-elapsed edits. Field-specific replacement and a precondition are established patch semantics; no public API change or JSON Patch dependency is necessary. [RFC 6902](https://www.rfc-editor.org/rfc/rfc6902#section-4)

## 4. Inherit the date and quantity independently of the data source

The unsuccessful meal-to-tracker turn selected an inherited operation twice. The resolver fills in the old operation before `_source` checks compatibility. The paired success selected `value`. In an offline control, `_source` rejected tracker calories with operation `food` and accepted the same metric with operation `value`. That reproduces the conflict; the privacy-safe trace does not retain the entire rejected clause.

Use typed quantity, source, aggregation, filter and scope separately. When the user changes intake to expenditure, inherit the day and energy dimension; discard the meal filter and food-specific execution method. For an exact day, the wearable adapter reads daily energy expenditure; food totals sum confirmed entries. For multi-day questions preserve an explicit total or mean and its denominator. Resolve the source first, then derive an admissible operation. Retry only genuinely ambiguous semantics. Test both directions on days with different food and tracker totals, two breakfasts on different days, and missing or draft meals.

## 5. Count metrics and test statistical hypotheses at their respective levels

Both flat explanations said 39 measures where their records covered 32 distinct metrics. `agent.py` combines tests by evidence ID and `findings.render_overview` counts records; immutable evidence versions are intentionally allowed. Keep those versions. For display, group comparable tests by metric, ordered periods and source. For statistical correction, determine whether records represent the same hypothesis using the test definition, metric(s), direction/lag, windows, source and analysis inputs. Deduplicate exact retests before adjustment where appropriate. Distinct hypotheses about one measure may warrant multiple tests; report them as such. Preserve the run-specific adjustment family and versioned citations. A display-only change cannot establish that adjusted p-values use the intended family. Test a duplicate retest, a genuinely different test of the same metric, and the 32-measure/39-record case.

## 6. Make the meaning of coaching evidence explicit at the tool

The wind-down suggestion survived the verifier because `analysis/coaching.py` itself labels a split on the stress tag as a wind-down option. In that comparison the app observed stress and sleep efficiency. It did not observe whether a wind-down routine was performed. Code-written prose and a valid option ID faithfully repeat the same semantic error.

Give each option a measured exposure, outcome, population/window, contrast and the strength of claim it permits. Validate these properties when producing the evidence. An observed stress association can support describing or monitoring that pattern. General wind-down guidance can be shown separately with a vetted citation. If actual routine observations exist, the tool can evaluate their association with outcomes; causal wording would require a stronger design. Review every existing lever for the same proxy-to-action substitution. Test that relabelling the same evidence cannot authorize a more specific intervention.

**One final renderer.** `ask._fill_points` can add guidance before the investigation branch calls `one_coaching_conclusion`, which rebuilds the answer with one option. Also, requested count is read by `asked_count` only when the plan is coaching. The saved outputs establish the omissions; they do not prove that three usable passages had already been found on each turn. Represent requested count, personal-only versus general-allowed, and the active comparison on the response request. Assemble verified observations, bound personal options and eligible general passages once. Then render once. When fewer options qualify, state how many were supported. Test general guidance unavailable, guard rejects a passage, one personal plus two general, and no eligible personal option. Check what is still present after reopening.

## 7. Separate formatting instructions from permission to remember

“Give me three options if possible. Label any general tips separately…” created two memory candidates. The accepted reading was `other`, with `told=True`. `reading_from` treats an OtherClause as something the person told the app. That coarse boolean removes the read-only veto in the API and the listener can infer preferences from the entire message.

Classify clauses as questions, commands for this answer, autobiographical assertions or explicit memory requests. Only a qualifying assertion or memory request can supply text to the listener, subject to existing consent rules. A response-format instruction belongs to this turn by default. Test the near-neighbors “Give me three options here,” “I generally prefer three options,” and “Remember that I prefer three options,” plus a mixed data question and explicit preference. Check candidates, approved records and the visible reply.

## Jev, instrumentation and delivery order

The reader chooses the analytical request; Jev supplies routing/classification and guard signals. Keep those roles. Jev can suggest investigate/coaching/guidance and evaluate the existing content boundaries. It cannot know whether the card changed, which dates were actually queried, or whether the underlying habit was measured. Do not add a second general LLM judge as a release dependency. The prior verifier-on run produced unnecessary clarifications. If Jev is evaluated for a specific ambiguous speech act, compare incremental accuracy, abstentions, latency and cost on identical frozen inputs against the existing reader.

1. Add private value-free stage diagnostics: selected authority (clock, result or draft), source of each changed field, normalized operation, requested versus executed length agreement, scope-propagation reason, unique metric versus hypothesis counts and final point counts. Save full intermediate structures only for synthetic audit fixtures. Capture initial and retry outputs separately.
2. Land deterministic fixes first: card patching, source transition, hypothesis/display counts, measured-exposure wording and single-pass rendering. Run the existing failing synthetic transcripts offline with real store state. Keep the passing counterexamples.
3. Prototype the constrained follow-up reader and persisted comparison context on a separate evaluation branch. Compare it to the current reader on the same fresh paired turns before replacing the production path. Report false clarifications and new-topic false inheritance alongside silent swaps. Verify normal API entry points, side reads and persisted citations.
4. Use [the existing acceptance criteria](acceptance-structured-requests.md) for release. Keep the 86 inspected turns as development cases. Freeze new questions before a paid run. Report by failure family and by paired wording; check raw scope, source, returned payloads, draft fields and memory state. Zero silent swaps and no unauthorized field changes are essential. A cheaper static replay answers whether the executor obeyed the plan; only a live held-out run answers whether the reader supplied the right one.
