# PR 195 reliability plan after independent audit v5

> **Historical record** (added to the repository on 2026-11-20), kept as written. It describes PR #195 before it was merged; #195 was merged on 2026-11-22 as `2ce08b5`. For what is true now, see [current.md](current.md).

**Decision:** keep the candidate under review. Preserve its deterministic statistics and direct lookup path. Concentrate changes at the points where a resolved request, a database fact or a supported finding stops controlling the answer. This is an implementation plan for commit `7ef95c7`, not a measured improvement. Read alongside [the scored audit](independent-audit-v5-handoff.md) and [the predeclared gates](acceptance-structured-requests.md).

## 1. Pin down what each change must preserve

Use the v5 results as development regressions. Replay *both* a failing example and the closest passing control through the same API with an isolated database, synthetic frame, local clock and scripted model responses. Where a trace records only an outline, label the reconstructed reader output as synthetic. A recorded “rolling/previous” alone does not establish that every argument in a first reading was correct.

Assert five things independently on each relevant turn: the requested metric/source and operation, resolved interval(s), tool result, visible text and citations, and state after reopening the conversation. Keep the individual assertions so a routing failure and a rendering failure are distinguishable. Retain the v5 private case IDs in test descriptions or the local test map. Only synthetic fixtures belong in the public repo.

- Preserve the 34 direct lookup controls, the second-of-two-results selection, the successful year-boundary calculation, the walking correction, both forget decisions, the successful squat and wind-down follow-ups, and the existing PHIA date controls. Keep single-step latency and model-call counts visible.
- Reproduce budget stops separately by forcing the same stop at the same stage. A correction that cannot complete must accurately report which draft remains. Report provider or harness exhaustion separately while still grading what the user saw.
- Make use of existing request attempts, request state, route, stop reason, action IDs and evidence IDs. If one stage cannot be localized, add a value-free reason code there. Avoid collecting raw health values or conversation text in production diagnostics.

## 2. Make date and comparison intent survive resolution

**Evidence.** In `short-01/t2`, the request trace already contained November 1–19 for “January 2027.” The coverage guard received the wrong window. In `edge-01/t2`, the first rolling reading was returned by the checker with reason `same_days`; the delivered answer collapsed to one day. In `registry-05/t2` the accepted rolling calculation produced October 14–19 for the six days following October 13–18. In `cuts-01/t2` the agent altered the endpoints when the intended edit was to exclude equality at the numeric threshold. “Boundary” on its own can be ambiguous; the previous count and the days exactly at threshold are relevant context.

**Implementation.** Start in `agent/clauses.py`, `agent/requests.py:period_window`, and `agent/checks.py:conflicts` (paths under `backend/app`). Reuse the current explicit, calendar, rolling and shifted interval forms. Add an explicit relation for a block adjoining a selected earlier interval if the current form cannot express it unambiguously. Encode the selected earlier part, which endpoint is the anchor, direction, inclusion and length. Distinguish an inherited interval from an inherited endpoint. Apply one deterministic calendar operation after reference selection:

| Instruction | Expected operation on inclusive dates |
|---|---|
| Next N days following [a,b] | [b+1,b+N] |
| Previous N days before [a,b] | [a−N,a−1] |
| N days ending on b | [b−N+1,b] |
| Shift the whole previous range by d | [a+d,b+d] |
| Count again excluding values equal to the threshold | Keep metric, dates and threshold. Change ≤ to < or ≥ to >. |

An explicit month and year constrain the requested interval, including future months. Preserve the app's current rolling and calendar conventions for “last 7 days” and “this month.” Validate literal anchors per clause before coverage checks. The existing checker can skip mismatched part counts or fall back to whole-message matching; require a clause-to-part mapping for checks that depend on local wording. An explicit length/end relation outranks the weaker observation that a phrase references “that day.” If two material interpretations survive, ask a targeted question identifying the competing choices. A retry must surface which constraint failed.

Pass the validated windows separately to investigation execution and delivery. Compare the focal evidence with the focal window and label any comparison baseline separately. For partial coverage, retain the asked-for interval and report usable days. For an empty frame, an entirely future interval, one missing metric, or one unavailable side of a comparison, state exactly what is unavailable. The current `outside_data` tests overall frame bounds and returns early when *any* interval overlaps; validate each metric/window separately where the answer depends on it.

**Proof.** Property-test interval length, adjacency and translation over varied anchor dates, leap years, year changes, lengths including one, and previous intervals of different lengths. Use paraphrase pairs that should produce the same interval and minimal pairs that should produce different ones. Put identical values on wrong and right days to force the test to inspect dates. Include an explicit calendar-month question with no prior turn, after a failed turn, and after a successful turn. Zero silent period swaps is a release gate.

## 3. Make each requested action and side read accountable

**Evidence.** In `mixed-01/t1` the reader already returned logging plus a side read. The subsequent route chose activity/clarify, the step read succeeded, and zero workout cards existed. The next turn was read as “other” and claimed the workout was drafted. In two status replies `ask._with_reads` appended the read's summary and merged its evidence without its claims. `db/chat.py:add_answer` stores cited evidence. Correct values arrived without inspectable evidence IDs.

**Implementation.** First fix the small, independently verifiable citation defect. Merge accepted side-read claims and evidence using the normal result path, preserve summary ordering, and make the API renderer display each result once. Check any downstream branch that clears claims when a card replaces the summary. Test the POST response, reopened chat, and fetching the cited evidence as the owner.

Next, preserve clause identity until execution is accounted for. `clauses.reading_from` currently selects a primary kind from a priority list and retains selected side fields. Represent each requested outcome internally with its clause, executor and completion result. Start with supported combinations (data plus workout, data plus status) and reuse the existing single-clause executors. An explicit validated workout clause must reach the workout proposal path regardless of the conversational classifier's suggestion. Use clause-local text and typed constraints for the proposal. Complete an independent read even when a draft needs one missing field; report both outcomes. Execute dependent clauses only after their referent exists. No new public endpoint is required for this first step.

In `api/chat.py:_answer`, build the action sentence from the actual proposal result and stored user-owned record. A pending card, an executed entry, an attempt with no card and an uncertain provider result need distinct wording. Never let free prose claim a draft or successful write without that state. A textual confirmation should point to the relevant card. Where more than one item could be meant, ask which. For a correction that supplies only a new duration, reuse the known payload and existing workout validation, retain start and derive end under the existing pause/explicit-end rules. Validate before superseding the prior draft. On failure the old draft remains actionable and the reply says so. Handle duplicate submits/retries using the existing action identity or idempotency mechanism after checking what the endpoint already guarantees.

**Proof.** Run both orders of read + draft, read + status with and without a waiting entry, correction of run and walk, missing duration, repeated correction, failed preparation, retry and reopen. Assert owner, action count, current payload, superseded state, exact duration, and every side-read evidence link. Exercise simulated persistence failure and confirm no external Google write occurs. Test a different workout and a different metric from the audited pair.

## 4. Resolve which records the question refers to

**Food and ambiguous counts.** In `food-01/t1` the first reading already selected operation food and a meal filter. It failed metric validation. The follow-up then lacked an earlier resolved food request. `requests.resolve` requires the combination of operation food and metric food_logs. Make the food clause describe the source once and select nutrient, meal filter, aggregation and date as fields. Translate that into the existing confirmed-food executor in `agent/requested.py`. An internally inconsistent source/metric combination is a reader-format error eligible for correction. A genuinely unrecorded nutrient is a data availability result. Never silently turn missing nutrients into zeros. Distinguish intake from wearable energy expenditure. In a follow-up, preserve the date while “everything I logged” explicitly clears the prior meal filter. Likewise distinguish a metric named “step count” on one day from counting how many days satisfy a predicate. In `boundary-01/t2` the accepted operation was conditional count despite the absence of a predicate. Validate operation against the object counted; ask for a threshold only when a predicate count is genuinely intended.

**Memory.** `chatonly-01/t1` was read as forget, its readback as other, and `fact-01/t4` as tracker status. Make the resource (chat statement, approved fact, pending action, saved tracker entry) explicit at dispatch. Keep storage permission separate from the user's requested action. A fact given for this chat can remain available in chat context without profile storage. A request to recall a fact grants no permission to create a preference based on the request itself. Carry this restriction through synchronous listening and the post-answer listener decisions in `api/chat.py`. Explicit mixed requests can still remember a separately stated fact through the normal approval card. Confirmed forget acts on one identified approved fact. Cancellation preserves it.

**Proof.** Seed meals on adjacent dates plus a draft meal and a confirmed entry with an unknown nutrient. Ask breakfast energy, all-meal protein, calories burned, and an empty day in sequence. Seed one approved fact, one pending fact, and one tracker draft simultaneously. Ask status of each, cancel forget, ask again, reopen chat, and try a different account. Check candidates as well as approved rows after read-only turns and after background work finishes. For “don't save this and remove my old goal,” verify the old-goal confirmation card and no new candidate. For the partner example vary who owns the observations independently of who asked the question.

## 5. Give investigations one evidence-backed conclusion

**Evidence.** Both coaching examples contradicted themselves in opposite directions. `ask.py` appends `coaching_fallback` when accepted claims contain no suggestion, even if the existing summary already makes a recommendation or says none exists. The API joins summary, claims and notes afterward. Checking only the submitted summary misses the contradiction. A measured correlation between sleep time and time in bed also has limited explanatory value because those quantities overlap by definition.

**Implementation.** Before rendering, choose one supported coaching outcome for the specific metric and period: an option supported by its habit evidence, no supported option among the tested habits, or insufficient usable evidence. Use that outcome to produce one recommendation/limit sentence with the relevant evidence IDs. Allow narrative about observations separately only when each claim is supported and consistent. If prose validation fails, render the accepted findings and outcome deterministically. Give overview findings their own claim and source IDs. For “why,” require a tested association on overlapping dates, or explicitly report which candidate explanations could not be tested. Identify part/whole or derived metrics before ranking explanations. They can describe an observation but should not win a ranking of independent explanatory factors. If other factors have weak evidence, name only those actually tested. Keep coaching observational and optional.

**Proof.** Use changed and flat profiles, a supported habit without an overall trend, a trend without a supported habit, a mechanically related metric, sparse paired days, a two-day request and an unavailable period. Inspect the final assembled API text, its citations and scope. Under forced model/tool exhaustion, return the verified scoped observations already available and explain the remaining limit. Never spend extra tool calls simply to manufacture an explanation.

## 6. Carry guidance context past both decision points; enforce the safety boundary

**Evidence.** The pushup follow-up failed in request resolution with “Which movement?”; retrieval was never reached. The Superman follow-up already had the right topic and ended as `lookup_declined`. In `agent/world.py:answer_world` the lookup chooser runs before the active passages are considered. A known topic rescues a “which” response, but other no-tool responses can still bypass the passages. An earlier successful pushup answer also cited unnecessary variants.

**Implementation.** Store the established topic/variant and IDs of the passages actually supporting the answer. Resolve a continuing reference to that topic before asking for clarification. For eligible public guidance, try the active vetted passage for the requested detail before generic source selection. If it lacks the detail, search within the same variant, check support, then answer or describe the gap. Keep the current limit of one safe rewrite. On explicit topic change, release the old constraint. Where two earlier topics fit, ask which. Filter displayed sources and saved active passage IDs to those that support the final instructions. Apply the existing content and urgent-response rules before any reuse of a passage.

In `boundary-01/t3` the trace shows the diagnosis request became an investigation with focus why. Check the user's original requested action before an investigation can override routing; preserve the established urgent and general wellness paths. Return the project's fixed boundary response for explicit disallowed requests, and run no unnecessary personal investigation. Test ordinary “what changed?” language beside explicit diagnosis requests to detect excess refusals.

**Proof.** Test one movement across setup, lowering, breathing, topic switch, ambiguous referent and unsupported detail. Use unseen variants and one nonexercise routine. Compare returned passages with the individual instructions. Exercise a no-tool chooser result with and without a relevant active passage. Assert a medical request is handled at the boundary even if a scripted reader labels it coaching or why.

## Delivery order, scoring and stopping

1. **First reviewable change:** the replay fixtures, citation persistence, truthful draft/status rendering and explicit-request safety boundary. Verify each via the API. These address observable wrong statements without changing benchmark arithmetic.
2. **Second:** date relations, constraint precedence and investigation coverage. Rerun all 34 direct controls and date-focused PHIA controls offline. A failed named-period gate blocks promotion.
3. **Third:** clause dispatch, correction handling and food/memory resource selection. Check database state through the real local API and existing confirmation endpoints. Run the backend suite after any reader-schema or dispatch change.
4. **Fourth:** investigation conclusion rendering and guidance continuity. Compare grounded advice and honest abstention on contrasting profiles. Run the relevant mobile contract checks if the implementation changes any returned shape. Keep all work on the unmerged candidate until the existing release gates pass.

**Evidence for release.** Keep development replay, fresh live conversations and PHIA scores separate. Use the original acceptance targets for fully correct responses: 90% direct data, follow-ups and memory; 85% logging and guidance; 75% investigations; at most 10% needless clarifications. Report numerator, denominator, partials, failures and infrastructure stops by area. Report strict memory answer correctness alongside state correctness. Keep the zero-event release gates and the PHIA allowance of at most one regression. Report false draft claims separately and require zero in the action tests. Report paired consistency as an additional diagnostic: how often *both* natural phrasings of the same intent pass. A good pooled score cannot compensate for a wrong-month answer or unauthorized state change.

**Budget and uncertainty.** The last recorded remainder is about $0.275. Before a live run, derive a hard bound from the actual deck, caps, retries and reserved PHIA allowance. Freeze unseen prompts, profiles, answer keys and scoring before execution. Favor new conversations in the weak areas over more identical metric openings. Cover both sides of each important distinction, including read vs proposed write, upcoming block vs shifted range, and supported advice vs insufficient evidence. If that budget fits only a small smoke check, report it as such; leave any larger release audit pending an explicit budget decision. Small denominators make a single turn move an area's percentage considerably. The project can credibly demonstrate consistent behaviors within a measured scope without claiming universal reliability.
